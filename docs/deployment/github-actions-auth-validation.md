# NexaSMS isolated authentication validation

## Purpose and isolation boundary

`.github/workflows/isolated-auth-validation.yml` runs the rejected authentication proposal only inside a disposable GitHub-hosted Ubuntu runner. It starts the Supabase CLI's local Postgres/Auth/API stack, applies all repository migrations with `supabase db reset --local --no-seed`, and tears the stack down in an `always()` step. It does not link a Supabase project, use hosted credentials, deploy Edge Functions, alter hosted Auth configuration, or contact the Velocity project. The local Supabase service keys are generated by the runner stack and remain within that job; the workflow does not print them or read GitHub secrets.

The integration suite creates temporary `@example.test` Auth identities and the minimum linked school/profile/staff records needed for authorization assertions. Those records exist only in the runner's disposable local database, which is destroyed at job end. No real-person or production data is used.

Reviewing the retry assertion against the SQL exposed a confirmed defect in the rejected migration: successful/terminal transitions clear the PII-bearing payload, while `reserve_provisioning_request` still compared that cleared JSON to a repeated caller payload. The proposal now uses the retained canonical payload hash for completed/terminal requests and retains the exact JSON comparison for nonterminal requests. The static assertion and real local integration scenario cover both a same-payload completed retry and a conflicting retry. This correction is local proposal-only and has not been applied anywhere.

## Runtime coverage limits

The CI job is defined but **has not run**. The repository currently has uncommitted work, and the user prohibited commit/push. GitHub cannot execute this new workflow until it is committed and pushed or otherwise made available on a GitHub PR. Therefore no migration, SQL, Deno, Auth/JWT, concurrency, RLS, or PHPUnit result is yet claimed.

After it runs, inspect any failures before treating the migration as approved. Some fault modes cannot be induced reliably in the real local stack (network timeout after Auth write, failed Auth compensation, lost PostgREST response, and exact lease-expiry race); the existing fake-service suite covers modeled variants only. The runtime suite currently verifies live lease renewal and competing claims, but does not wait ten minutes to test a real database lease expiration/reclaim. A real concurrent owner wave tests the database-level single-owner lock/index; school and staff provisioning are performed for separate tenants and tenant reads are checked under real Auth JWTs.

The Laravel job establishes compatibility of the existing provider behavior with nullable password rows; it does not test Laravel database migrations against Supabase PostgreSQL.

## Commands used by CI

```sh
supabase start
supabase db reset --local --no-seed
node supabase/tests/authentication-foundation-static.mjs
psql "$DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/authentication_foundation.sql
deno test --allow-env --allow-net supabase/tests/provisioning-recovery.test.ts
deno check supabase/functions/*/index.ts supabase/tests/authentication-provisioning.integration.ts
deno test --allow-env --allow-net --allow-run=psql supabase/tests/authentication-provisioning.integration.ts
vendor/bin/phpunit tests/Unit/LegacyPasswordUserProviderTest.php
supabase stop --no-backup
```

No `supabase link`, `supabase db push`, hosted migration, Edge Function deployment, account provisioning in hosted Auth, or Vercel deployment is part of this workflow.

## Running it and approval boundary

The workflow listens for pushes and pull requests targeting `deployment/vercel-supabase-poc`, plus manual dispatch. Since committing and pushing are not authorized, a project owner must publish the reviewed workflow (or open a PR containing it) before GitHub Actions can produce actual results. Review every failing log and resulting diff; do not apply the rejected migration to the existing hosted project based only on a passing isolated run. An independent security review and explicit production approval remain required before hosted SQL or function deployment.
