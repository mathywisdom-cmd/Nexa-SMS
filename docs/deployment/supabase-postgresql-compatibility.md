# PostgreSQL compatibility review

Status: static source review only. No local PostgreSQL, Docker, Supabase CLI, or remote Supabase connection was used. No SQL was executed.

## Verified in Laravel source

- Laravel is 8.42.1 (`composer.lock`); migrations use Laravel Schema Builder and query builder. Search of all 35 migration files found no handwritten MySQL DDL, SQLite PRAGMA, or driver-specific raw SQL.
- Foreign keys for legacy tables are attached in `2019_09_22_142514_create_fks.php` after all those tables exist. No explicit circular FK chain was found in the migration declarations.
- PostgreSQL supports the modeled integer IDs, varchar/text, dates, timestamps, JSON, indexes, uniqueness, and declared FK delete actions.
- `DB::raw('COUNT(*)')` and conditional aggregate expressions in application services are generic SQL forms. Audit-log JSON access uses Laravel JSON query helpers; PostgreSQL JSONB operators are available, but exact generated SQL should be exercised under the target connection.
- The schema and query code use Eloquent/query builder broadly; no application raw MySQL/SQLite query was found in the reviewed code.

## Definite adaptation required

| File | Source construct | PostgreSQL concern | Target treatment |
|---|---|---|---|
| `2018_10_06_225007_create_pins_table.php` | `used` and `times_used` are strings with numeric default `0` | PostgreSQL may reject an unquoted numeric default for varchar | If preserving varchar, use `DEFAULT '0'`. Consider a typed small integer only as a separately reviewed app/data migration; it is not a behavior-neutral assumption. |
| `2018_10_31_192540_create_book_requests_table.php` | `returned` is string with numeric default `0` | Same varchar/default issue | Use `DEFAULT '0'` if preserving type. |
| `2014_10_12_000000_create_users_table.php` | `photo` default calls `asset('global_assets/images/user.png')` | Runtime helper can embed an origin/host and is not portable SQL | Use a relative key or NULL as a schema default; verify all consuming accessors/views before moving the actual file. |
| all migrations using `unsignedInteger` / `unsignedTinyInteger` | unsigned integer types | PostgreSQL has no unsigned integer | Use signed PostgreSQL types; add nonnegative / appropriate range checks where valid. Do not add checks blindly to ID columns unless data semantics confirm. |
| identity columns | Laravel increments | `serial`/sequence behavior differs when preserving/importing existing IDs | Prefer `GENERATED BY DEFAULT AS IDENTITY`, allowing import of explicit legacy IDs; reseed identity sequences after import. |

## Risks requiring verification on PostgreSQL

- Migration 30 does data updates, unique-index replacement, nullable FK operations, and seeds a default school. A clean-schema SQL version must omit the DEFAULT School insert (user explicitly requested no demo data); an existing-data import requires a separately ordered transform.
- Migration 34 dynamically derives year and term records from legacy `year`/`term` columns then backfills IDs. It is an upgrade data migration, not just DDL. Run it only as an explicit data conversion plan after legacy records are imported and validated.
- Migration 35 generates unique school slugs in PHP. For imported schools, slug generation must handle collisions identically or produce a reviewed replacement mapping.
- The Laravel schema's scalar foreign keys do not themselves prove that two connected rows share the same `school_id`. Target PostgreSQL should add composite same-school FKs using unique `(school_id,id)` parent keys where practical.
- Nullable columns in composite unique constraints permit multiple NULL values in PostgreSQL. This can matter for optional school codes, payment references, class types, exam references and timetable values. Confirm desired semantics; use partial unique indexes only where the application requires “unique when present”.
- Constraint/index names are global within a PostgreSQL schema for some object types. Preserve explicit names where present (`attendance_class_section_date_unique`, `attendance_record_student_unique`) and namespace generated names to avoid collisions.
- PostgreSQL folds unquoted identifiers to lowercase; all source names are lowercase, avoiding case-sensitive quoted-name traps.
- PostgreSQL `LIKE` is case-sensitive by default while MySQL collations often are not. Search behavior should be checked for school/user lookups.
- Laravel pagination, transactions, and parameter binding are expected to work through PDO PostgreSQL, but application runtime requires `pdo_pgsql` and correct SSL settings. This was not tested.
- Supabase transaction poolers may not preserve session-level settings and can constrain named prepared statements depending on pooler mode/version. Avoid reliance on session `SET`, temporary tables, advisory locks, or persistent prepared state; verify the selected Supabase pooler behavior before choosing it. Prefer transaction-scoped operations and supported connection parameters.
- The draft uses PostgreSQL's column-list form of `ON DELETE SET NULL` on composite same-school FKs so deleting an optional related row does not null out the required `school_id`. This requires a PostgreSQL version supporting column-targeted SET NULL (PostgreSQL 15+); confirm the target Supabase engine version or replace these constraints with equivalent triggers/restrict behavior after review.
- `auth.users` UUID linkage is a new target relationship, not in the 35 migrations. It must not replace existing integer IDs; use a unique nullable `auth_user_id uuid` bridge during staged identity migration.

## Data and authorization query concerns

`App\Models\Concerns\BelongsToSchool` applies a school scope only when `TenantContext` has a school; with no context, ordinary server-side queries are not automatically tenant-filtered. The context is populated by `InitializeTenantContext` and school-host resolution. Platform super-admins are represented by `users.school_id IS NULL`. This Laravel behavior must **not** be copied as an RLS fallback: absence of a school claim must result in denial.

Role checks use `users.user_type`, `roles`, `role_permissions`, and `user_permissions`. `PermissionService` treats `super_admin` as platform-scoped and applies per-user overrides before role grants. The marks routes now check `marks.view` or `marks.manage` at action boundaries. RLS designs need equivalent permission semantics; a SQL role name alone is not sufficient authorization.

Student/parent/teacher access depends on `student_records.user_id`, `my_parent_id`, `section_id`, `sections.teacher_id`, and `subjects.teacher_id`. Marks/results contain multiple related IDs and need same-school plus relationship checks. The PIN-gated marks page also depends on Laravel session `pin_verified`, which cannot be reproduced by a plain row policy. Direct client access to PIN and marks rows should remain denied until a secure server-side result operation reproduces that workflow.

Payment recording updates payment records, creates receipts and audit logs; wrap in one transaction and lock the target row to prevent concurrent overpayment. Attendance batch save verifies the submitted student IDs equal the section roster; use a server-side transactional operation. No corresponding SQL function is verified in the current application.
