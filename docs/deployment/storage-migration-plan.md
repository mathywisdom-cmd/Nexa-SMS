# File storage migration plan

**Status:** mapping only. No files were copied and no bucket/policy was created.

## Current implementation

- `config/filesystems.php` defaults to Laravel `public` disk at `storage/app/public`; generated URLs are `APP_URL/storage/...`, conventionally served through `public/storage` symlink.
- `SupportTeam\StudentRecordController`, `SupportTeam\UserController` and `MyAccountController` upload photos with `storeAs()` and save an absolute `asset('storage/'.$path)` URL into `users.photo`. User/staff uploads use role/code-based folders; student photos use student/code folders.
- School logo uploads are handled by `SuperAdmin\SettingController`; school model has `logo` and settings can store a public-upload path. Inspect actual setting/logo path formats before import.
- Existing views render `users.photo`, school logo, and student photo URLs in dashboards, lists, profiles, marks, parent children, payments and receipts.
- Payment receipt PDFs are generated by DomPDF at request time (`PaymentController@pdf_receipts`); the currently visible flow returns a download/view. A legacy fallback writes a receipt HTML file on Laravel's local disk. PDF generation need not necessarily be a stored object; decide retention requirements first.
- Student documents/attachments must be inventoried by scanning actual `Qs::getUploadPath()` helpers and file input names before data export. The current visible forms show profile photos; do not assume photo-only uploads.

## Supabase Storage mapping

| Existing object | Target bucket/access | Suggested object key and metadata |
|---|---|---|
| NexaSMS platform logo/brand assets | Public bucket only if intentionally public | `platform/branding/{object}`; store relative object key in config, not old localhost URL. |
| School logos | Usually public read, authorized school-admin write | `schools/{school_id}/branding/{object}`; verify active membership and `settings.manage` on writes. |
| User/staff profile photos | Public read only if the school policy intends all authenticated users to see them; otherwise private authenticated | `schools/{school_id}/users/{legacy_user_id}/profile/{object}`. Restrict writes to own profile or authorized user manager. |
| Student profile photos | Prefer authenticated/private or public read only after school policy review | `schools/{school_id}/students/{legacy_student_record_id}/profile/{object}`. Tenant boundary in `storage.objects` policy. |
| Student/guardian documents | Private bucket, authenticated policy or short-lived signed URL | `schools/{school_id}/students/{student_id}/documents/{opaque_object_id}`. Parent access must verify linked student, not just school membership. |
| Receipts and financial attachments | Private by default; signed download after tenant/finance permission check | `schools/{school_id}/receipts/{receipt_id}/{opaque_object_id}.pdf`; generated PDF may remain download-only if no retention requirement. |

Avoid putting email, student name, admission number, phone, or other personal data in object paths. Keep a database `file_objects`/attachment record with school ID, owner/entity type+ID, bucket, object key, MIME, size, hash, visibility and timestamps; that record also enables authorization checks and migration reconciliation.

## Security policies and URL behavior

- Create separate public-branding and private-record buckets where public visibility is truly needed. Default student files, receipts and documents to private.
- Enable RLS on `storage.objects`; policies validate `bucket_id`, the school folder, authenticated user's active membership and role, and parent-child/teacher assignment when relevant. Do not trust a client-supplied path segment as the sole tenant check.
- For upload `INSERT`, constrain allowed key prefix, file size/type in trusted validation, and tenant. For replacement/upsert, authorize `SELECT` and `UPDATE` in addition to `INSERT`; deletion needs a separate policy. Never use a service key in Vercel browser code.
- Generate signed URLs server-side/through Storage only after record-level authorization; choose short expiry and prevent URL leakage in logs/referrers. Public bucket URLs are permanent/public and unsuitable for private records.
- Supabase Storage policies apply to `storage.objects`; test upload, list, read, replace/upsert, move/copy and delete for admin, teacher, parent, student, platform owner and foreign school. Confirm allowed APIs and limits in the current Storage docs before implementation. [Storage access policies](https://supabase.com/docs/guides/storage/security/access-control).
- Store relative object keys in Postgres, not full localhost URLs. Replace current `asset('storage/...')` consumers with a disk-aware URL resolver. Preserve legacy URL reads temporarily during migration; do not break local data before every reference has been mapped.

## Safe copy and cutover plan

1. Inventory all files under local public storage and other upload roots; produce a manifest (legacy URL/path, owner row, school ID, MIME/size/hash) without committing PII.
2. Identify duplicate, missing, orphaned and external URL entries. Keep source files and create a separate backup before any copy.
3. Create buckets and RLS policies in a non-production Supabase project. Test policies with real Auth identities and multiple schools before uploading private data.
4. Copy objects preserving a reversible mapping from old path to bucket/object key. Verify count/size/checksum and associated user/school/receipt references.
5. Deploy code that resolves both old/new references if a staged cutover is required; test image rendering, signed downloads, receipts and deletion semantics.
6. Switch new uploads, verify no writes reach local filesystem, retain source backup during agreed rollback window, and only delete old copies after explicit retention approval.

No current upload implementation should be replaced until path inventory and privacy classification are complete.
